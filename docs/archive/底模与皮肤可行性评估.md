# 底模与皮肤：可行性评估

状态更新（2026-09-18）：用户已批准第二批开发，现已分离稳定布局与默认皮肤，并完成微缩建筑和六位居民。尚未开发第二套皮肤或切换界面。以下保留此前评估内容，实施结果以《第二批微缩沙盘交付记录》为准。

## 结论

可行，适合小镇长期迭代。建议将底模定义为“场地与场所的稳定结构”，以模块化组件表现；在其上替换视觉主题。底模可以有默认的简化外观，但不必将所有建筑合并成一个大模型。

当前处于体量验证阶段，业务逻辑少，适合在正式建筑细化前建立这套边界。现有工程有基础，但尚未具备完整换肤能力。

## 1. 哪些内容保持稳定

| 层次 | 内容 | 作用 |
| --- | --- | --- |
| 场地结构 | 海岸轮廓、地面高度、道路连接、六个场所的位置与占地 | 保持空间布局和动线 |
| 场所身份 | 稳定 ID、名称、功能类型、父子关系及未来业务入口 | 保持教学楼始终对应同一个教学场所 |
| 交互规则 | 镜头限制、未来点击区域、入口点与标签锚点 | 避免更换外观破坏操作 |
| 视觉皮肤 | 配色、材质、建筑造型、绿化、标牌样式、灯光和环境 | 决定用户看到的小镇风格 |

换皮肤默认不改变建筑的位置、场所功能或业务链接。如果还要改变海岸形状、道路和占地，则作为布局版本调整，单独验证。

## 2. 皮肤可以换到什么程度

### 配色与氛围

更换海水、沙岸、草地、道路和建筑颜色，以及光照、天空背景、界面与标签样式。可沿用已有几何体，制作和适配工作相对较少。

### 建筑与环境造型

同一教学楼地块可挂载不同的教学楼外观，同一绿化位置可选用不同植物。造型既可以来自程序化组件，也可以在后续获准后采用单栋 GLB 模型。

例如：现有蓝白滨海主题可换成未来科技主题，教学楼仍位于原地、仍使用同一场所 ID，但建筑外壳、屋顶、植物和灯光可以改变。

这类皮肤需要实际设计和制作对应的模型组件，不是给一张图片就能自动变成完整小镇风格。

### 季节或活动装饰

可作为独立装饰层叠加在已选主题上，例如灯饰或活动旗帜。装饰层和换肤都属于后续功能，当前不实施。

## 3. 模型约定

为了让不同造型可靠替换，每个场所需要约定：

- 同一坐标单位、朝向、中心原点与地面高度。
- 可用占地和合理的高度范围，避免挡路或遮住其他场所。
- 入口点、名称标签位置，以及未来交互点击范围。
- 轻量资产预算，控制几何体、材质、贴图、透明效果和阴影的开销。
- 个别皮肤缺少某个场所模型时，使用基础外观兜底。

位置与业务身份保存在场所配置中，皮肤按场所类型或场所 ID 选择对应的外观组件。运行时优先只加载当前使用的皮肤资产，避免一次加载全部主题。

## 4. 对现有代码的判断

已有基础：

- `data/places.ts` 已有稳定 ID、场所类型、位置、占地、名称和未来入口字段。
- `data/town-config.ts` 已集中配置场地轮廓、道路及镜头。
- 地面、道路、建筑体量和植物已分为独立组件。

需要后续调整：

- 建筑颜色、体量高度与场所身份数据目前混在一起，需要明确哪些是布局约束、哪些是皮肤参数。
- 部分颜色和造型细节仍直接写在组件中，需要抽到统一视觉配置。
- `TownMassing` 目前按场所类型直接生成体块，需要增加可替换的建筑外观映射。
- 3D 颜色、标签、界面和灯光需要共同引用主题，避免只换建筑而界面风格不协调。

因此不需要推倒重建，但也不能宣称现在已经能一键更换任意风格。

## 5. 建议的下一步（未授权开发）

如果用户认可方向，下一批先做内部结构整理：

1. 将布局与场所身份作为稳定底层。
2. 抽出当前滨海风格的颜色、材质和灯光配置。
3. 建立每类建筑外观的替换接口，保留当前默认体量。
4. 验证整理前后的场地位置、功能身份和默认画面一致。

先形成一套可扩展的默认皮肤，不必立即制作多个主题或增加切换按钮。后续用户确认第二套外观时，再制作并验证真正的换肤能力。未来是否由管理员统一换肤，或允许每个游客自行选择，也应届时单独确认。
