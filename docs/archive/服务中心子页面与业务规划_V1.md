日期：2026-09-19。状态：规划稿，尚未开发。需用户确认首批范围及申请规则后实施。

最新修订：用户要求身份和申请事项可在后台配置，分荣誉称号与权限称号，支持公开展示、权限绑定、展示板和NPC介绍。V1的两类固定申请范围已被《服务中心身份称号与权限规划_V2.md》替代，前台子页面和进度布局继续参考本稿。

## 一、定位和现状

服务中心是小镇的接待与办事入口：帮助游客了解小镇，帮助居民申请学习或共创身份，帮助工作人员处理申请并给出可追踪的结果。

目前已有3D服务中心建筑、固定门口导航、手机号本地登录、个人资料、运营/超管框架；前台办事页、申请数据、审核权限、业务身份和结果通知尚未实现。

采用同域名网页子页面，建议公开路径 `/service`，沿用场所ID `civic-hall`。第一批不制作建筑内部3D场景。

## 二、前台页面

### 服务中心首页

- 顶部：公司品牌、五六零AI服务中心、返回小镇、个人中心。
- 欢迎区：“在这里，开启你的小镇学习与共创之旅”，配简洁服务中心建筑画面或品牌插画。
- 已登录区：当前身份、待处理申请、需要补充的材料；游客展示“先了解服务，需要办理时再登录”。
- 主服务卡片：申请成为学员、申请OPC共创、我的申请。
- 辅助内容：办理流程、常见问题、服务说明。服务时长和联系方式只展示实际配置的信息，不虚构承诺。
- 与现有小镇一致的浅蓝白色、圆角卡片和清晰图标，适当采用服务中心自身建筑的色彩作为点缀。

### 服务详情与申请

建议路径 `/service/apply/student`、`/service/apply/opc`。

先展示面向人群、需填写信息、审核过程、通过后的身份及明确权益，再进入表单。游客可以看介绍，提交前登录，登录后回到原办理事项。

流程为“了解事项 → 填写信息 → 确认提交 → 查看进度”；手机单列，桌面主表单加说明栏。草稿保存到本人账户，刷新不丢失；不能把私密申请草稿放入公开配置或公开内容接口。

### 我的申请与详情

建议路径 `/account/applications` 与 `/account/applications/[id]`，服务中心和个人中心链接到同一份记录。

- 列表：事项、申请编号、状态、提交时间、最近更新时间。
- 详情：本人提交内容、状态时间线、对外处理意见、下一步操作。
- 需补充时明确指出要修改哪些内容，编辑后再次提交；旧提交版本保留。
- 审核通过后显示获得的业务身份，以及已开放的后续入口。学院/园区业务未开放时明确说明，不提供失效链接或虚构权限。

## 三、首批事项及字段建议

| 事项 | 面向对象 | 建议填写内容 | 审核通过 |
| --- | --- | --- | --- |
| 学员申请 | 所有愿意学习AI的居民 | 联系称呼、学习方向、AI基础、学习目标；学校/单位为选填 | 增加“学员”业务身份 |
| OPC共创申请 | 希望参与AI创业、项目或内容共创的个人/团队联系人 | 联系称呼、个人/团队情况、擅长方向、共创想法、所需支持；作品链接选填 | 增加“OPC共创成员”业务身份 |

手机号直接关联已验证的注册账户，不在表单重复收集或修改。普通用户查看本人信息；审核员默认看到脱敏手机号，首批通过站内处理意见沟通，不默认开放手机号导出。

首批建议不收身份证、证件照、营业执照或附件，先用文字和可选作品链接。作品链接仅作为人工查看资料，不由服务器自动抓取。

“学员申请”是学习需求登记和服务对接，不是考试或专业资格认证，不因用户没有AI基础而设置门槛。平台业务身份也不等同于实名核验。

一人可同时拥有居民、学员和OPC成员身份；身份不改变用户昵称或后台管理角色。注册用户默认只有居民身份，游客公共浏览继续保留。

学校合作建议第二批单独做：学校/机构名称、联系人、合作方向、预计人数及需求；记录“合作意向→对接→结果”。提交或通过意向申请不自动创建学校管理员、班级或课程权限。

## 四、状态和处理规则

标准流程：草稿 → 待审核 → 已通过 / 需补充 / 未通过。

- 草稿：本人编辑、保存或放弃。
- 待审核：提交内容冻结，可由本人撤回；修改需先撤回或由工作人员退回补充。
- 需补充：显示具体补充要求；本人修改后重新进入待审核，保留历次内容。
- 已通过：生成业务身份授权记录，不重复发放同一身份。
- 未通过：显示原因，允许修改后重新申请，旧记录仍可查询。
- 已撤回：不再进入审批队列，可以复制原资料重新申请。

同一用户同一事项只允许一个进行中的申请；已有有效身份时展示当前资格，不再显示重复申请按钮。

审批、撤回和重复点击须由数据库事务处理：两个工作人员同时审核，只有首次有效操作成功；另一方读取最新状态。审批通过与身份发放必须原子完成，不能出现申请已通过但身份没有生效。

已通过申请不能随意改成未通过。需要纠错时由超管执行独立的身份撤销并填写对用户可见的原因，保留原审批和撤销记录；不删除用户其他身份或历史内容。任何未来课程/项目授权是否随身份撤销失效，应由对应业务单独定义，不能默认全删。

## 五、运营中心的服务中心模块

入口：运营管理中心 → 版块管理 → AI服务中心。

| 子页面 | 功能 |
| --- | --- |
| 办理概览 | 待审核、需补充、近期处理数量，按真实记录统计，无数据时明确为空 |
| 申请管理 | 按事项、状态、编号/称呼筛选，分页查看 |
| 申请详情 | 申请资料、提交版本、时间线、处理记录及可执行操作 |
| 审核处理 | 通过、要求补充、未通过；退回/拒绝必须填写明确意见，通过也记录处理说明 |
| 服务内容 | 编辑本模块介绍、办理说明和FAQ，支持草稿、预览、发布 |
| 身份记录 | 查询经服务中心授予的学员/OPC资格；撤销由超管执行 |

第一批不做批量通过、手机号导出、任意表单设计器和复杂审批流。每份申请单独查看和处理。对用户显示的处理意见与仅工作人员可见的内部备注分开，若首批无内部备注需求则不增加该字段。

## 六、超管配置和审核权限

- 超管管理事项是否开放、资格说明和审核岗位；运营人员维护日常服务内容及处理申请。
- 事项对应身份固定为学员或OPC成员，不允许通过配置把“审核通过”映射为管理员或超级管理员。
- 第一批表单字段固定，仅提供已实现事项的开关和说明，避免没有后端规则支持的任意配置。
- 增加明确的服务中心审核授权、服务内容维护授权；由超管赋予指定运营人员。不能因为现有账户role=admin就自动得到所有申请资料的访问权。
- 可由超管直接处理，但不能审核本人申请；本人申请由另一位有权限的工作人员处理。
- 每个接口核验账户最新角色与岗位资格，不能只靠前端隐藏按钮。
- 暂不建立学校/班级范围；这类实体尚未存在，不提供无效的授权选项。

关闭事项只停止新申请；已经提交的申请继续处理，历史记录仍然可见。说明或条件更新仅影响新申请，旧申请保存提交时的事项说明版本，避免规则变更后无法追溯。

## 七、个人中心与结果提示

个人中心增加：

1. 我的身份：居民、学员、OPC成员，有效状态和授予日期。
2. 我的申请：状态、需补充提醒和处理结果。
3. 服务中心入口：从现有“探索更多身份”区域进入具体服务。

首批提供申请结果的站内提示和未读标识，点开后标记已读。不扩展成全站聊天系统，也不发送真实短信或邮件。

## 八、3D场景入口与返回

- 点击服务中心建筑的明确入口按钮可打开子页面；行走到门口时显示“进入服务中心”，按E或点击进入。
- 沿用现有“前往服务中心”导航，只负责到达固定门口；到达后由用户主动进入子页面，不自动跳转。
- 与现有E键坐下/NPC交互共享优先级，不能一次按键同时触发两项动作；门口入口触发范围避开长凳和NPC交谈提示。
- 服务子页面提供“返回小镇”，返回服务中心门口，保持明确的浏览上下文；普通重新打开首页仍按现有规则显示欢迎页。
- 服务页面可通过公开URL直接访问，不必先加载整个3D场景。登录后的回跳只允许本站明确支持的页面。

## 九、数据边界与实现方向

独立保存事项、申请、提交版本、处理记录、业务身份授予、站内结果提示和审核岗位。服务内容使用草稿/发布版本；申请保存提交时的表单和事项版本快照。

账户信息继续复用已有用户表；业务身份独立于role字段。三个中心读取同一份业务数据，不能各存一份状态。

公开接口只提供已发布介绍、条件、FAQ和开放状态；本人接口只读取本人申请和身份；审核接口限定岗位资格。知道申请ID不能读取其他居民资料。错误响应、日志和公开统计不泄漏申请正文和联系方式。

未来需要材料附件时必须新增受控私有文件机制；不能复用现有公开Logo/站点图片接口。

## 十、建议实施批次与验收

### 第一批：完整的申请办理流程（建议下一次确认）

1. 服务中心首页、详情、申请表、我的申请及进度详情。
2. 学员和OPC两类固定申请，草稿、提交、撤回、补充、通过、未通过。
3. 运营中心申请列表与详情、服务内容草稿/发布、审核操作与真实概览。
4. 超管指定审核人员、事项开关、业务身份撤销纠错。
5. 个人中心身份与申请记录、站内结果提示。
6. 3D服务中心入口、明确的返回小镇路径，保留原行走和NPC交互。

### 后续

- 第二批：学校合作意向、组织与班级对接，必要时补充私有附件。
- 学院开发阶段：课程/班级资源授权、学习记录；服务中心仅提供资格和申请对接。
- 创业园开发阶段：团队、项目、园区入驻；OPC身份不直接代表项目成员或获得办公空间。

首批验收：游客可了解、登录后回到原事项；刷新不丢已保存草稿；申请重复/并发审批可控；通过后身份同步；退回意见可见并可补交；普通居民无法查他人资料、未获授权运营员不能审核；自己不能审批自己；关闭事项不丢历史；未接入业务不显示虚假权益；桌面和手机可完成全流程；原场景交互回归通过。

## 十一、需用户确认的业务选择

建议：第一批只开放学员与OPC共创申请，学校合作放第二批；两类先采用人工审核；学员申请定位为学习登记和对接，不设置AI基础门槛；先收文字信息，不收证件和附件；身份通过后不自动授予全部课程或项目权限。

用户确认这组选择及第一批范围后，再开展页面和业务实现。
