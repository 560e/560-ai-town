## 本次部署问题与处理结论

| 现象 | 原因与处理 | 当前结论 |
|---|---|---|
| 已有服务却找不到deploy.json | 删除源码/配置后，systemd与town560账户仍可能保留；原提示把缺配置误称其他根目录 | 同项目失效布局可交互备份修复，异目录不接管 |

| proxy_set_header: command not found | 把Nginx配置当SSH命令执行 | 属宝塔反代配置；当前反代注册已正常，不再修改 |

| 首次安装摘要显示`.deployment`或旧`town560`账户用途不同 | `.deployment`是项目内运行状态目录，不是源码根；旧版受限运行账户的Home仍指向历史路径 | 摘要会分别显示项目根、状态目录和本次输入的数据库。当前V0.0.5仅复用非root、`nologin`的专用`town560`账户，并把其Home切换到新项目状态目录；旧目录不删除。其他账户用途不明时仍停止 |
| Next提示外层package-lock被忽略 | 嵌套项目目录与运行账户home触发根目录识别警告 | 本次未阻止编译/启动，不与健康检查403混淆 |
| Turbopack报`.local/site-assets`链接越出filesystem root | 候选版本构建前挂载了指向共享上传目录的运行时链接，Turbopack拒绝追踪候选根外文件 | V0.0.3起构建期间仅注入部署环境；构建成功后才挂载`.env.local`和`.local` |

## 邀请码注册：首次启用与日常维护

最新完整0.0.1修订包包含邀请码功能，安装时自动增量建表。新库默认关闭邀请码限制：先用手机号密码注册本人账号，执行`sudo bash manage-linux.sh admin`授权超管，重新登录进入“系统管理后台 → 账号与注册”，生成邀请码并保存，再开启“注册时要求邀请码”并保存设置。

每批1–100个邀请码，每码仅用于一次成功注册。完整码只在生成后显示一次，请立即复制或下载妥善分发；后台历史记录仅显示摘要、状态和使用者，不能找回完整码。未使用码可停用。注册事务失败不会消耗；账号创建成功但网络中断时，请先尝试使用已设置密码登录，不要重复注册。关闭邀请限制后可正常注册，旧未用码保留，重新开启后仍有效；已有用户登录始终不需要邀请码。

只有超级管理员可配置和生成邀请码；不授予邀请用户管理员或认证称号。真实短信未接入，本地测试OTP在邀请开启时不能创建新账号（已有账号可登录），新用户使用密码邀请码注册。删库重装将清除全部旧邀请码及使用记录，旧码不再有效。

## 当前完整修订包：安装、检查、修复与彻底重装

2026-09-23完整部署修订包已包含数据库权限和Host健康检查两次补丁，不需要逐个打补丁。以最新tar.gz旁车SHA256为准；旧包与旧补丁保留为历史，不叠加到新包。正常安装会先校验包内FILES.sha256；自改发布源码后应重新生成发布包，不要绕过校验。


若宝塔终端把`sudo`的标准输入识别为非TTY，当前V0.0.5会在加载部署助手前把输入、输出和错误输出统一绑定到当前会话的`/dev/tty`，继续显示菜单。没有`560-town.service`是首次安装的正常状态，不会再导致菜单前退出。若该终端没有控制终端，脚本会明确退出且不改动系统；请改在SSH或宝塔的交互终端执行，或先运行`sudo bash deploy-linux.sh --check`收集只读诊断。不要使用`bash -x`运行真实交互部署，以免将私密输入写入终端记录。

检查不重启运行服务。修复仅接管同一根目录的已知失效布局，不接管其他站点；活动服务须先安排停止。没有部署记录时，先备份旧unit/账户信息，再处理失效unit、校正专用账户home；不会删除旧数据库或素材。配置仍存在但current缺失时，列出构建和配置有效的候选，要求输入确切版本，不自动挑最新；不会回退数据库。权限不足默认管理员postgres（回车保留），密码隐藏输入，仅本次使用；保留host/port/TLS，只授予public的USAGE/CREATE，用应用账号复查。连接/版本错误、旧表所有权问题仍明确停止。

### 0.2 准备数据库

Debian12/13、Ubuntu24.04可直接在向导选“1=自动新建本机PostgreSQL15+”，填写新的库名、应用用户名、至少12位密码；向导安装数据库并创建对象。同名对象不会覆盖，不要先手动建同名对象再选自动新建。

Ubuntu22.04必须先准备PostgreSQL15+实例，向导只连接已有实例。宝塔已管理数据库或自行建库时也选“2=已有PostgreSQL15+”。由数据库管理员准备**全新专用库和角色**的例子如下；名称可替换，但须与向导一致。在已有本机PostgreSQL上执行：

```bash
sudo -u postgres psql -d postgres
```

远程实例改用`psql -h 数据库主机 -p 5432 -U 数据库管理员 -d postgres -W`，按服务方要求验证TLS证书。在psql逐条运行：

```sql
SHOW server_version;
CREATE ROLE town560 LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password town560
CREATE DATABASE town560 OWNER town560;
\connect town560
GRANT USAGE, CREATE ON SCHEMA public TO town560;
\q
```

`\password`隐藏提示并要求重复密码；不要把真实密码写进SQL或命令参数。若角色/库已存在，跳过CREATE和改密，先核对用途和所有者，使用原凭证；管理员连接正确库后仅补足`GRANT USAGE, CREATE ON SCHEMA public TO town560;`。旧库迁移还需要对已有应用表具有相应权限，不用超级用户角色掩盖对象归属错误。

用应用账号验证本机数据库，非本机则替换主机/端口并按服务方要求配置TLS：

```bash
psql -h 127.0.0.1 -p 5432 -U town560 -d town560 -W
```

```sql
SELECT current_database(), current_user,
       current_setting('server_version_num')::int >= 150000 AS version_ok,
       has_schema_privilege(current_user, 'public', 'USAGE') AS usage_ok,
       has_schema_privilege(current_user, 'public', 'CREATE') AS create_ok;
\q
```

三个检查应为`t`。确认`pg_dump --version`主版本不低于服务器，否则先准备匹配客户端；尤其Ubuntu22.04默认客户端可能为14，不能据此备份PG15+。

### 0.4 宝塔或已有Nginx配置HTTPS反代

域名解析到服务器，在宝塔为其配置有效HTTPS证书。公网只开放需要的HTTPS及证书验证入口，应用和数据库端口保持内网。模式3安装器**不接管HTTPS站点、不申请证书**。

在域名已有**443 HTTPS server块**中保留证书、日志及独立ACME规则，替换原`location /`，不要追加重复location。安装后的`.deployment/shared/https-proxy.conf.example`按实际端口生成，可由root查看。以下为56043示例。移除宝塔静态扩展名缓存location、PHP解析和`try_files`；删除指向项目目录的`root`/`alias`或改指独立空目录。除受控ACME验证目录外，所有应用请求都交给上游，不让静态location绕过反代下载文件。

```nginx
client_max_body_size 8m;
location ~ (^|/)\. { return 404; }
location / {
    proxy_pass http://127.0.0.1:56043;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
}
```

80端口仅做HTTPS跳转及独立ACME验证。ACME例外只指向证书验证目录，不指项目根；不用`location ^~ /`绕过隐藏文件拦截。`.env.local`、`.deployment`及配置/备份、源码不得由本站或其他站点的root、alias、下载目录公开。边缘代理覆盖Host和转发头，不能直接透传访客伪造值；应用校验Host及X-Forwarded-Host等于保存域名、X-Forwarded-Proto为https，写请求还校验Origin。用真实HTTPS域名，不伪造localhost打开测试验证码。

使用宝塔配置检查、保存和重载；系统Nginx可执行：

```bash
sudo nginx -t
sudo systemctl reload nginx
curl -I https://opc.560e.com/
curl -i https://opc.560e.com/api/account
curl -I https://opc.560e.com/.deployment/shared/deploy.json
curl -I https://opc.560e.com/.env.local
curl -I https://opc.560e.com/package.json
```

宝塔Nginx未必注册为`nginx.service`，使用其面板对应操作。账号接口应显示`enabled: true`、`password: true`、`local: false`；敏感路径及源码应404且不返回文件内容。最后用浏览器实际验收注册、登录、刷新保持会话、退出、PC/手机地图及受保护页面；本次未替部署者执行服务器验收。

从新解压源码更新既有安装，明确原项目根：

```bash
sudo bash /新源码目录/deploy-linux.sh --install-root /既有项目根
```

先在原安装执行`sudo bash manage-linux.sh backup`并核对完成，再将新包校验并解压到独立候选目录，不覆盖原项目或其`.deployment`。从候选目录维护旧安装的例子：`sudo bash manage-linux.sh --install-root /srv/560-ai-town status`。不要删除`/opt/560-town`或旧站点来绕过冲突；旧布局按第4节先明确迁移。

候选源码不会成为第二安装根；从`.deployment/current`或release内执行也回到既有根。先复用原配置检查/构建候选，成功后暂停旧服务、备份、迁移、切换和启动。原认证模式不会因升级变成模式3。候选检查失败不切换现用版本；切换后失败尝试恢复旧代码及systemd。首次启动失败会停服务并解除current，保留配置和候选，使下次仍检查端口。

代码回退不等于数据库自动回退。数据恢复优先恢复到新库并保留现场，使用匹配客户端`pg_restore --no-owner --no-privileges`，凭证走交互或私密环境。先在临时目录核对素材和配置，再调整连接、权限及匹配代码。不要直接解压覆盖系统根或删除原库。迁移工具保留的旧代码、home及systemd备份供回退；本轮没有实际恢复数据库。

“正在展开小镇”排查顺序：

1. `systemctl show 560-town -p WorkingDirectory -p ExecStart`：核对实际运行版本。
2. `systemctl status 560-town --no-pager`、`journalctl -u 560-town -n 80 --no-pager`及本机上游响应。
3. 浏览器检查JS/CSS和异常；开发模式检查HMR来源、真实Host和缓存。首页200不代表3D已初始化。
4. SSH失败查本地隧道端口；域名失败查DNS、证书、Nginx和上游端口。
5. ENOSPC分别查容量/inode和候选/依赖/日志；保留真实数据、配置和备份，日志按轮转策略处理。

真实主机验收仍需覆盖安装/重试/升级/旧迁移、HTTPS密码注册与会话、桌面/手机3D、双账号互见/私聊、服务申请审批、角色隔离、Logo持久化、备份及恢复。本次发布验证证据见发布记录，不能据Windows检查宣称Debian/Ubuntu实装通过；新源码包不代表服务器已更新，历史包保留原记录。

## 7. 版本与发布规则

`VERSION`、`package.json` 与 `package-lock.json`（含根package记录）保持一致。修复/小调整递增补丁位，如0.0.1→0.0.2；完整新模块递增次版本，如0.0.2→0.1.0；重大不兼容升级递增主版本。1.0.0代表用户确认的首个正式标准，不自动根据日期决定。

开发/候选阶段可在功能状态标注目标 `Vx.y.z-dev` / `Vx.y.z-rc.1`，这是阶段标记，不代表正式包。**当前打包脚本只接受纯数字三段版本**；本轮不更改工具支持，暂不将预发布后缀写入打包版本字段。将来确需候选包命名支持再单独完善工具。

每批更新状态表和CHANGELOG的“未发布”区域；只有正式发布时创建 `docs/releases/Vx.y.z.md`，记录日期、功能/修复、验收、已知问题、配置和数据库变化、升级/回滚、源码定位及包名/校验。使用 [版本记录模板](releases/版本记录模板.md)。不提前创建看似已发布的未来版本文件。

发布步骤：

1. 确认版本范围及验收，确认源码和发布版本一致，状态表分别记录本地/服务器/包；现有目录没有Git元数据时不编造commit，以发布清单哈希定位文件。
2. 同步版本字段、手册与CHANGELOG，创建该版记录；包内带当时的手册及文件清单，供维护旧版。
3. 运行批准范围所需验证；确认发布允许清单排除配置、密钥、数据库、上传、依赖及构建缓存。
4. 执行 `npm run release:pack`，核对 `RELEASE-MANIFEST.json`、`FILES.sha256` 和压缩包旁 `.sha256`。同名包已存在会拒绝覆盖，保留旧正式包，正常修复发新版本。
5. 压缩包SHA只能在包生成后计算，记录在外部对应版本文档与旁车校验文件；它不可能写入同一个已经生成的包内，否则校验会改变。包内清单记录每个源码文件哈希。
6. 获授权部署后更新实际服务器状态与日期；未部署写未部署。发布记录保留当时事实，后续问题进入下一版；补充勘误须注明日期，不能重写历史。

`docs/archive/` 保留历史，不作为日常阅读入口。现有打包清单包含docs子目录，新的正式包会包含手册、版本记录和历史资料；本次经用户明确要求按当前源码重新交付V0.0.1，先保留历史包及校验，再生成新包；此例外不代表今后可无记录覆盖正式包。历史测试与备份细节见归档，不当作今日已复测。


## AI学院外链课程维护

1. 使用已有运营管理员或超级管理员，从“版块管理 → AI学院”进入站外课程管理；普通居民无管理权限。
2. 新建课程，填写名称、简介、完整HTTP(S)网校地址与排序，上传可选PNG/JPEG/WebP封面（最大4MB）。没有封面自动使用默认图。
3. 勾选发布并保存后出现在居民目录；取消发布并保存即下架。封面上传后还需保存课程。修改冲突时刷新课程列表重新编辑，防止覆盖他人修改。
4. 居民在教学楼按E或点击打开课程弹窗，点击前往网校学习后另开标签页。网校可能要求另行注册登录；小镇不管理网校账号、报名、费用或进度。
5. 原课时编辑、审核、报名及进度入口已移除。旧表和上传文件保留备份用途，不提供历史学习产品入口，也不自动生成外链地址；运营需填写真实网校链接。

升级当前源码前执行标准 `npm run db:migrate`，新增academy_external_courses表，保留旧库旧文件。数据库与`.local/academy-assets`（部署时shared/local对应目录）须成套备份；不得因接口下线删除旧文件。所有学院API保持不使用公共CDN缓存。

外链课程已包含在用户确认部署的V0.0.1中；V0.0.2新增场景窗口与注册昵称，尚未部署。校园几何、固定出生、私有页面返回和多人房间规则保持不变。
